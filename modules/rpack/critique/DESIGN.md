# rpack and rhost

A database built on [Rdb](../rdb) has three parties:

- the **developer** designs the catalog (its schemas and table groups) and releases versions of it;
- the **admin** of a database deploys releases into it;
- every **device** admits the releases its software can handle, replicates the data, and projects it into a local SQL database that the app reads and writes.

`rpack` is the developer's tool. It turns a catalog source into signed releases, each written to a release file. `rhost` runs on every device, the admin's included. It installs the releases the app ships, deploys them where the device's key has the authority, syncs, and keeps the projections current. Both are libraries with a command-line front end.

The two sides live in different repositories. A catalog has one repository, on a single branch, holding every release it has made. Each app target (desktop, web, server, and so on) has its own repository with ordinary branches, and keeps a copy of the release files it ships.

## Releasing with rpack



### The catalog repository

```
editor/
  rpack.json              name, signing key, and which folder made which release
  .gitignore              work/*/build/ and work/*/stage/
  releases/               the release files, and nothing else
    editor-1.5.0-3f9a1c2e.rpack
    editor-2.0.0-8b21d0aa.rpack
    editor-1.5.1-c09e77f1.rpack
  work/                   one folder per version
    2.0.0/
      version.json        the releases this one builds on, and its note
      target-catalog.sql  the catalog as it should be after this release
      upgrade-manual.sql  optional ALTER SCHEMA steps the diff cannot infer
      test-data.sql       rows rpack stage inserts after deploying this release
      staging.json        how the staging app projects and syncs
      .released/          what the release was made from
        target-catalog.sql
        upgrade-manual.sql
        update.sql
      build/              generated by rpack build; not committed
        update.sql
      stage/              generated by rpack stage; not committed
    2.0.1/
      ...
```

Everything rpack needs is in these files, and it never reads git history. Keeping every release in one place is what lets it reason about upgrade paths. A version's folder is named after it: `2.0.0`, or `2.0.0-8b21` if two releases ever share a version. It stays after the release, so any release can be staged later, and its test data and staging config can still be edited. `.released/` holds the signed inputs and `update.sql` as they were when the release was made, which is how rpack tells whether a folder still makes its release. `build/` and `stage/` are outputs.

`target-catalog.sql` describes the desired state: `CREATE SCHEMA` statements and one `CREATE CATALOG`. It has no `ALTER`. A group may say `AT LATEST`; a hash or a version set may not, because the release pins each group's schema. A catalog `VERSION`, `NOTE`, or `BY` may be written when it agrees with the release (the folder's version, `version.json`'s note, and `rpack.json`'s key); `rpack new` removes a catalog `VERSION` that names a parent. A schema may state its own `VERSION`, which needn't follow the catalog's numbering: a release that creates or changes the schema gives it that version, and a changed schema's version must be above the one it has. A schema that states a `VERSION` it doesn't have, with nothing changed, is refused. A schema with no `VERSION` takes the release's. rpack computes the alters. The signed release still supplies the release version and the signature.

```sql
CREATE SCHEMA hhs:user CREATORS ($dev) AS ( ... );
CREATE SCHEMA hhs:doc CREATORS ($dev) AS ( ... );

CREATE CATALOG editor CREATORS ($dev) PARAMS (:admin identity) AS (
  TABLEGROUP user USING SCHEMA hhs:user
    USING IDENTITIES identities
    WITH ROWS (
      identities (keyId = :admin, publicKey = publicKey(:admin), name = 'Admin'),
      caps (label = 'manager', grantee = :admin)
    ),
  TABLEGROUP doc USING SCHEMA hhs:doc
    BIND user => user
    USING IDENTITIES user.identities
);
```

```json
{
  "name": "editor",
  "key": "dev",
  "released": {
    "1.5.0": "editor-1.5.0-3f9a1c2e",
    "1.5.1": "editor-1.5.1-c09e77f1",
    "2.0.0": "editor-2.0.0-8b21d0aa"
  }
}
```

`key` is a label in the developer's keystore (`~/.rdb/keys.json`, shared with `rdb`). `released` maps each released folder to its release, and `rpack release` writes it. A folder that isn't in it is a version under way.

A folder's `version.json` holds what its release is besides the catalog:

```json
{
  "base": [
    "editor-2.0.0-8b21d0aa",
    "editor-1.5.1-c09e77f1"
  ],
  "note": "tags, and the 1.5.1 fix"
}
```

`base` names the parents, and is `[]` for the first release. `note` is optional; when present it is the release's note, a non-empty string. Any other field is refused, so a typo doesn't pass for a setting. `rpack new` writes the file without a note, and whatever rewrites `base` (`set base`, a re-release) keeps the note.

### Commands

The commands find the repository by walking up from the current folder, or from `-C <dir>`, to `rpack.json`. The ones about one version run inside its folder, anywhere under `work/<version>/`.

```
rpack init <name> [--key <label>]           scaffold a catalog repository here
rpack new <version> [--base <release> [+ <release>]...]
                                            start work/<version>/ on its base, with its starting files
rpack set base <release> [+ <release>]... [--force]
                                            put this folder on another base, and write its starting files again
rpack status                                this version, its base, and a count of what it would sign
rpack build                                 write build/update.sql; on success, print that it did
rpack release [--force] [--yes]
                                            sign it and write it to releases/; --force re-releases
rpack stage [--passphrase-stdin]            build a staging app for this version in stage/
rpack log                                   the release history, its upgrade paths, and the versions under way
rpack verify <file>                         check a release file offline
rpack export <store.db> <catalog> [<version>] [--out <dir>]
                                            write a release made in the rdb REPL to a release file
```

A release is named by version, by version and tag (`2.0.0-8b21`), by name, or by `#hash`, and a base of several is written `a + b`. `rpack export` is the bootstrap path for a release made by hand in an `rdb` workspace: it writes that release's file.

### Starting a release

`rpack new <version>` starts `work/<version>/`. Its base is the `--base` releases or, by default, the releases below the version that aren't already in the past of another one (see below). The version must be above every parent, and a version already released or a folder that already exists is refused. Several versions can be under way at once, each in its own folder, and renaming one is `git mv`.

`new` prints one line, the folder and its base, and writes `version.json` and the starting files. `target-catalog.sql` is the highest-version parent's `.released/target-catalog.sql`, verbatim, comments included, with every table, column, group or param the other parents changed written in, and any `CREATE CATALOG` `VERSION` equal to a parent's version removed; schema `VERSION`s are left for you to edit. The result describes the parents' merged state exactly, so a release made from it unchanged only settles the versions the parents disagree on. `staging.json` comes from that parent's folder, and `upgrade-manual.sql` and `test-data.sql` start empty. The first release starts from a skeleton.

`rpack set base` moves a folder to another base and writes its starting files again. Work on the current base stops it: an `upgrade-manual.sql` or `test-data.sql` that isn't empty, a `target-catalog.sql` whose model differs from the base, or a `staging.json` that differs from the base's copy. `--force` discards that work. In a released folder, a new base is a change like any other, released with `rpack release --force` (see [Re-releasing](#re-releasing)).

### Assembling a release

A release goes from its parents to `target-catalog.sql` in five steps:

1. Start from the parents in `version.json` (see below).
2. Apply `upgrade-manual.sql`: the explicit steps the diff must not guess.
3. Diff the result against `target-catalog.sql`. Every difference becomes schema rules (add or drop a table or column; set foreign keys, restrictions or concurrent deletes) and a catalog release (new groups, and new schema versions for existing ones).
4. Write one update per changed schema, with the hand-written rules first and the generated ones after. Each changed schema takes the `VERSION` it states in `target-catalog.sql`, or the release's version.
5. Write the catalog release, pinning the new schema versions.

`rpack build` writes an accepted draft to `build/update.sql` and prints that it did. The file's header says not to edit it: the statements are the previous releases, then the steps in `upgrade-manual.sql`, then the difference from `target-catalog.sql`. A refusal is printed and nothing is written. A source error prints `Error assembling <version>` and then the file and line. `rpack release` signs the draft, with `version.json`'s note, and writes the release file, then `.released/` with `target-catalog.sql`, `upgrade-manual.sql` and the `update.sql` it signed, then the folder's entry in `rpack.json`. It never touches the working files, which stay with their version.

The diff refuses two kinds of change, with the reason:

- **Redefining a column in place,** meaning its type, default, nullability or constraints, or flipping a table's identity-provider flag. The only rule for that is drop plus add, which resets the values.
- **Changing an existing group's bindings, gates, identity provider or genesis rows.** Group definitions are immutable, so this needs a new group.

When a reset is what you want, `upgrade-manual.sql` says so and the diff completes it:

```sql
ALTER SCHEMA hhs:doc AS (
  DROP COLUMN pages.title
);
```

With `target-catalog.sql` giving `pages.title` its new type, the diff sees the column missing and adds it back. Drop plus add in one update is the reset.

The version number is yours. If a release drops something, or changes foreign keys, restrictions or concurrent deletes, without a major bump, rpack warns and still releases.

### Versions and upgrade paths

Releases form a DAG. By default `rpack new` picks a release's parents from its version: every release with a lower version that isn't already in the past of another one. Every release follows the same steps whatever its version. For example:

- `2.0.0`**,** when 1.5.0 is the newest release: its parent is 1.5.0.
- `1.5.1`**, released after 2.0.0.** Its parent is 1.5.0, so `rpack new 1.5.1` starts `target-catalog.sql` from 1.5.0's source, and the patch is an edit to it.
- `2.0.1`**:** its parents are 2.0.0 and 1.5.1, so it carries the patch. `rpack new 2.0.1` starts `target-catalog.sql` from 2.0.0's source with 1.5.1's changes written in. Leaving any of them out of the release is then an ordinary edit.

```
rpack new 1.5.1                  # parent 1.5.0; target-catalog.sql from work/1.5.0/.released/
(cd work/1.5.1 && rpack release)
rpack new 2.0.1                  # parents 2.0.0 and 1.5.1
(cd work/2.0.1 && rpack release)
```

`--base` (or `rpack set base`) names the parents explicitly, for example to leave a lower release out, and the version must be above every parent. The draft then warns about the lower releases outside the new release's past: a database running one of them would run it alongside the new release, as below, until a later release includes it.

A database can move to any release that isn't at or below one it has deployed. From 1.5.0 to 2.0.0 is a plain upgrade. From 1.5.1 to 2.0.0 merges the two: the database runs **2.0.0 + 1.5.1** until it deploys a release above both. Where both changed the same thing, the higher version wins, and then the hash. Schemas carry their own versions for this: every `CREATE SCHEMA` and `ALTER SCHEMA` has a `VERSION`, increasing along the schema's history. rpack gives a schema defined in the catalog repository the version of each release that changes it, unless `target-catalog.sql` states the schema's own. Outside rpack the clause may be left out: a create defaults to `0.0.1`, an update to the next patch.

Two releases can end up with the same version, for instance when two developers release at once. So release files are named with a tag, the first 8 hex digits of the release hash: `editor-2.0.0-8b21d0aa.rpack`. Where a typed version is ambiguous, add the tag: `2.0.0-8b21`.

`rpack log` shows the DAG, the lower releases that no higher release includes yet, the released folders whose files changed since their release, and the versions under way with their bases.

### Re-releasing

A release that turns out wrong before it's shared can be made again. After editing its folder, `rpack release --force` there replaces the release with one made from the folder's working files. When the folder still makes the release (the same base, the same `update.sql` as `.released/`, and the same note in `version.json`), there is nothing to re-release. A new note alone is a change, and the re-release carries it.

The new release is drafted as if the old one had never been made: in a scratch replica of every release file except the one replaced and the releases built on it, its dependents. No other file carries those in its past, or it would be a dependent too, so the scratch replica is what `releases/` will hold afterwards.

Each released dependent is made again on the new release, by version, from its own folder's working files, on its base with the replaced names mapped to the new ones, and with the note in its `version.json`. A dependent that doesn't build fails the whole re-release, and nothing is written. Its folder is what it releases, so a change the re-release made that the dependent's `target-catalog.sql` doesn't have is undone in the dependent; that shows up in its warnings, as a drop without a major bump, for instance. A dependent whose files changed since its release ships those changes too.

On a terminal, rpack shows what it's about to do and asks. It lists the release replaced, then each dependent with its count and warnings, marked `(changed since release)` where its files changed, then each version under way on a replaced release, since that folder was written against the old one. Without dependents it asks before the passphrase, as a release does; with them, after, since they can only be made on the signed new release. Nothing is written before the answer. Without a terminal, a re-release with dependents needs `--yes`.

The writes go in an order that never leaves a release missing: the new release files; each folder's `.released/`; the dependents' `version.json`; the `version.json` of each version under way on a replaced release, repointed to the new names; `rpack.json`; and last, the removal of the replaced files. An interrupted run leaves extra files, never missing ones.

A replaced file that was already shared stays a valid release. A replica that has it would hold it next to the new one of the same version, which is why this is for releases nobody has yet. Re-releasing the first release makes a new catalog: replicas of the old one take none of its releases.

### Release files

A release file is JSON: a manifest, and every signed entry in the release's past, with the developer's signatures exactly as made. Installing one verifies every entry and needs no keys. Release files are what app repositories copy.

Files are pretty-printed with sorted keys, so the same release always gives the same bytes and diffs between releases stay readable.

### Staging

`rpack stage`, in a version's folder, builds a staging app in its `stage/`: an ordinary rhost app with one host, named `default`. Once built, it's managed like any other app:

```
rhost --app work/2.0.0/stage status
sqlite3 work/2.0.0/stage/hosts/default/db/data.sqlite
rdb work/2.0.0/stage/hosts/default/rdb/replica.rdb --keystore work/2.0.0/stage/keys.json
```

It rebuilds every time, since it follows the folder's files, and a failed stage leaves the previous one in place.

Staging replays every release in the version's past, in version order: each one is shipped, deployed, and then given its own rows from its folder's `test-data.sql`. So staging 2.0.0, whose parents are 1.1.0 and 1.0.1, deploys 1.0.0, then 1.0.1, then 1.1.0 (the merged state), then 2.0.0. A released folder that still makes its release ends with that release file, and needs no key. Any other folder ends with its release as it would be made now: rpack signs it with your key, deploys it, and nothing leaves that folder. Before the first release the creators are stand-in keys, so no passphrase is needed.

Each upgrade therefore meets the rows of every release before it, and each release's rows are written in that release's shape. In sample rows, `$labels` are stand-in keys, and `$admin` is the staging database's admin:

```sql
INSERT INTO user.identities (keyId, publicKey, name) VALUES ($alice, publicKey($alice), 'Alice') BY $admin;
INSERT INTO user.caps (label, grantee) VALUES ('writer', $alice) BY $admin;
INSERT INTO doc.pages (title, deleted) VALUES ('Welcome', false) BY $alice;
```

The staging app keeps those stand-ins in a keystore of its own, `stage/keys.json`, each with an empty passphrase, so the host runs unattended; it signs as `admin`. `staging.json` follows rhost's split: `mesh` is the host's network settings, written to its `host.json`, and `allow`, `projection`, `autoDeploy` and `params` go to `app.json`. `releases`, `keystore` and the host's key are staging's own, and any other field is an error. A param a release declares takes its value from there, and an identity param defaults to `$me`, the staging admin; a name the staged release doesn't declare is an error. At the end rpack projects the database once, so `db/data.sqlite` is current without the host running, and prints what the last deploy did to the rows:

```
staged editor-2.0.0-8b21d0aa in work/2.0.0/stage/: 1.0.0, 1.1.0, 2.0.0
deploying 2.0.0:
  doc   pages: 3 rows changed; blocks: 5 rows gone
  user  no change
rows: work/2.0.0/test-data.sql
```

After `rpack new 1.5.2`, `rpack stage` in `work/1.5.2/` stages 1.5.1 and deploys the planned 1.5.2 on top.

## Hosting with rhost



### An app and its hosts

An app can use one database or many; a chat app, for example, has one per server the user belongs to. On a device the app is a folder, with the release files it ships and its settings, and each database it serves is a **host**, with a folder of its own:

```
my-app/
  app.json            the app's settings, the same for every host
  catalogs/           the release files this build ships
  hosts/
    default/
      host.json           written by create or join: the database, the key, the network settings
      rdb/replica.rdb     this host's replica
      db/data.sqlite      its projection, which the app uses
      files/<mount>/      its file mounts, if the app has any
      run/                the running process: rhost.lock, rhost.sock, rhost.log
    gaming/
      ...
```

An app with a single database has one host, named `default`. `create` and `join` name a new host `default` unless told otherwise. `status`, `update`, `start` and `stop` act on every host unless one is named, and `serve` uses `default`, or the only host there is.

Hosts share the app's releases and settings, and nothing at runtime. Each has its own replica, so names stay unique within a host, and removing a host is deleting its folder. Each signs with its own key and syncs over its own network connections, as a peer of its own, so a peer met in one host learns nothing about the others through them. With the CLI, each also runs in its own process.

`app.json` holds what the app ships, the same on every device:

```json
{
  "releases": "catalogs/",
  "params": { "admin": "$me" },
  "autoDeploy": "minor",
  "allow": ["user.identities.keyId"],
  "projection": {
    "path": "db/data.sqlite",
    "indexes": [
      { "name": "by_label", "group": "editor", "table": "notes", "columns": ["label"] }
    ]
  }
}
```

- `releases` is the folder of release files this build ships, copied from the catalog repository. For each catalog, rhost uses the newest one. Its major is the newest one the app's code understands, so each host admits every deployed release below the next major and holds anything newer.
- `params` are the values for creating a database, and for the params later releases declare. `$me` is the host's key, and `$<label>` another key in the keystore. Every name must be a param the shipped release declares.
- `autoDeploy` decides when a host gets the shipped release, where its key has deploy authority. `minor`, the default, deploys patch and minor bumps; `major` deploys anything; `none` waits for `rhost deploy`. Only a release whose version is above every deployed one is deployed automatically.
  - Authority itself is not configured. It is each database's own rule (its creators, and each group's `ALLOW DEPLOY IF`), so a host deploys in a database it created and never in one it joined.
  - A release that declares a param `params` doesn't set is held too. The host keeps the release it has, `rhost status` names the missing param, and `rhost deploy --param` supplies it.
- `allow` is who may replicate with the app's hosts. It lists columns such as `user.identities.keyId`, and a peer is accepted when its key appears in one of them. Without `allow`, everyone is. Each app target sets it as part of its own release, and no host replaces it.
- `projection` is the target and, when `indexes` or `indexPub` is set, the index spec this platform uses. Its path is relative to the host folder and stays inside it; `rhost init` writes `db/data.sqlite`. No path the config names may take `host.json`, `rdb` or `run`, which the host keeps for itself. The declarations are written in rdb names and shared by every host. Omitting both leaves an already installed spec alone.
- `keystore`, optional, is a keystore file of the app's own, relative to the app folder. Without it, keys stay in the user's keystore (`~/.rdb/keys.json`, `RDB_KEYSTORE` or `RDB_HOME`), the one `rdb`, `rpack` and `rkeys` use, so the app folder holds no keys.

`host.json` records what the user did when creating or joining the host:

```json
{
  "database": "<database id>",
  "catalog": "editor",
  "created": true,
  "key": { "label": "me", "keyId": "<key id>", "publicKey": "<public key>", "passphrase": "env:EDITOR_PASS" },
  "mesh": {
    "scope": "internet",
    "discovery": [{ "type": "tracker", "url": "wss://tracker.example-corp.com" }],
    "transports": { "ws": { "listen": "ws://203.0.113.10:7400" } }
  },
  "autoDeploy": "none"
}
```

- `key` is the key the host signs with: the app's writes, any deploys, and the sync handshake. One host, one writer. The host finds it in the keystore by key id, so relabeling it there changes nothing, and `whoami` and the client read the public key from here, without the keystore. The passphrase comes from `prompt`, from `env:<VAR>`, or from nowhere for a key stored without one.
- `mesh` is how the host meets peers, the same document as `app.json`'s `mesh` and `\sync`. `scope` is `internet` or `localhost`. `discovery` lists trackers (`url`, `key`), folder discovery (`root`), and `broadcast-channel`. `transports.ws.listen` is a dialable `ws://` address; `transports.webrtc.signal` is a `wss://` signaling server with no endpoint id. A host key replaces that key from the app. On `internet`, omitted WebRTC listens at `wss://signal.mypeer.net:4612`. On `localhost`, omitted WebSocket listens at `ws://127.0.0.1` on a free port. Two hosts of an app can't listen on the same WebSocket port.
- A host may also replace `app.json`'s `params`, `autoDeploy`, `projection`, or `mesh` with its own. `releases`, `keystore` and `allow` are always the app's.

Both files are strict: a field rhost doesn't know, at any depth, is an error that names it.

Whatever a host's key can do in its database, creator authority and identity rows included, stays with that key. Hosts that must not be linkable each get their own key; separate network connections don't help while a key is shared.

### Commands

Commands act on the app in the current folder, or in `--app <dir>`. Run from a host folder, `<app>/hosts/<name>/`, and a command with no host name acts on that host. `create` and `join` still name a new host `default` when none is given, and `remove` still requires the name.

```
rhost init --release <file>... [--param <name>=<value>]...
                                                 write app.json and copy the release files into catalogs/
rhost create [<host>] [--catalog <c>] [--name <n>] [<host options>]
                                                 create a database from the shipped release, with the host's key as creator
rhost join <database-id> [<host>] [<host options>]
                                                 fetch an existing database
rhost remove <host>                              stop it and delete this device's copy
rhost update [<host>] [--yes]                    install the shipped release, admit, deploy if due; then exit
rhost deploy [<host>] [--version <v>] [--param <name>=<value>]...
                                                 deploy now, whatever autoDeploy says, for example a new major
rhost start [<host>]                             start hosts, each in its own background process
rhost stop [<host>]                              stop them
rhost serve [<host>]                             run one host in the foreground
rhost status [<host>]                            shipped, deployed, adopted and held releases; members; peers
rhost events [<host>] [--after <id>]             rejected and voided writes
rhost whoami [<host>]                            the host's public key, to send to an admin

host options:
  --key <label>                  a key in the keystore, by label or #<key id>
  --passphrase-env <VAR>         unlock it from $VAR instead of asking
  --mesh <json>|@<file>        mesh settings; scope is asked when neither this nor app.json sets one
```

`rhost init` only describes the app, and writes no keys. It asks for each param the shipped releases declare that its flags leave out; identity params default to `$me`.

`rhost create` and `rhost join` set up a host, and ask for what their flags leave out:

- **The key:** a numbered list of the keys in the keystore, with "Other" to type a label when there are more than eight, and "Create new key pair", which is made in that keystore.
- **The scope:** internet or localhost.

They record the passphrase source as `prompt`, or as `env:<VAR>` with `--passphrase-env <VAR>`, for an unattended host. Without a terminal, `--key`, a mesh `scope`, and `--passphrase-env` are required.

Each host runs in its own process. `rhost start` starts one in the background for each host that isn't running, or for the one named. It unlocks each host's key first, asking for each key's passphrase once, so a missing key or a wrong passphrase fails before anything starts. It hands the passphrase to the process over a pipe, and returns when each one reports that it's serving. That report is a single line on a pipe that closes afterwards. `rhost serve` runs one host in the foreground, for service managers such as systemd, launchd or a container. A running host holds `hosts/<name>/run/rhost.lock`, logs to `hosts/<name>/run/rhost.log`, and listens on `hosts/<name>/run/rhost.sock`. `rhost stop` signals the process named in the lock, and the socket goes away with the process.

On start, a host updates: it installs the shipped release (a no-op when the entries are present), admits, deploys when due, starts sync, opens the projection and installs the index spec. Nothing watches `hosts/`: a host that the app or the CLI creates or joins starts when asked, for example with `rhost start <name>`.

Status lists each host's deployed releases, such as `2.0.0 + 1.5.1`, and reports two conditions:

- **Upgrade required:** a newer major is deployed there and held.
- **Host behind:** the app ships a release that the host hasn't deployed. Status says why: `autoDeploy` is `none`, the release is a major bump and `autoDeploy` is `minor`, the host's key isn't a creator, or the release declares a param `params` doesn't set. In that last case a second line names the command that supplies it:

```
behind    1.2.0 needs a value for :moderator (identity), which params don't set
          set it in app.json's params, or run: rhost deploy default --param moderator=<value>
```

The releases, the members and those two conditions come from the host's store. Peers and the last error come from `run/rhost.sock`, so they appear only while the host is running. `rhost update` prints the same reason when it holds a deploy.

`rhost deploy` deploys the shipped release, or the one `--version` names (`2.0.0`, `2.0.0-8b21`, or `#<hash>`), whatever `autoDeploy` says. It runs in its own process on the host's store and unlocks the key itself, and a running host picks the deploy up. The key must still be allowed to deploy, and a release at or below a deployed one is refused. A release that declares new params needs their values, from `params` or from `--param <name>=<value>`, written `$me`, `$<key label>` or as a JSON value. On a terminal it asks for any still missing; without one it fails and names the flags to pass. A param is set once and the database keeps it, so nothing is written to `app.json`.

`rhost events` lists the rejected and voided writes from the projection, and `rhost whoami` prints the host's key from `host.json`. Both work while the host is stopped, without the keystore. With no host named, `deploy`, `events` and `whoami` use `default`, or the only host there is.

A bare `rhost status` shows every host. A bare `rhost update` asks before updating several; `--yes` skips the question.

`start` never creates a database. `create` and `join` are explicit, so a misconfigured device can't start a new host by accident, and neither starts the host it makes.

`rhost remove` deletes this device's copy of a host, stopping it first. The database lives on in every other replica that has it.

The other commands work while a host runs. So does `rdb hosts/<name>/rdb/replica.rdb`, which opens a host's replica in the REPL with the same keystore (an app with its own passes it with `--keystore`). The replica store serves several processes, and the running host picks up what they write, deploys included, and syncs it. The one thing to keep in mind is that admitting a release is permanent for that replica, so `\adopt` in the REPL admits it for the app as well.

The release file is how a release enters a database: the admin's host installs it and deploys it. Every other replica receives the new entries by sync and admits them when they're below its next major. For those replicas, the release file sets that major and lets the first start work offline.

## The app

While a host runs, the app works on its projection, `db/data.sqlite` unless configured otherwise, with plain SQL, from any language. Tables are named `<group>_<table>`. Writes are optimistic. The host ingests them, signs them with its key, and replicates them, but a write can still fail afterwards: it is rejected at ingestion when it breaks a rule, or voided later when a concurrent change wins, such as a revoked permission or a deleted parent. Either way the row returns to its replicated state and an event is logged.

`rhost_client` is the interface for what plain SQL doesn't cover. A Node app gets it from `rhost_client_node`, given the host's folder:

```ts
import Database from 'better-sqlite3';
import { isHostStatus } from '@hyper-hyper-space/hhs3_rhost_client';
import { openClient, projectionPath } from '@hyper-hyper-space/hhs3_rhost_client_node';

const dir = 'my-app/hosts/default';
const db = new Database(projectionPath(dir));          // projection.path from host.json or app.json
const client = openClient(dir, { db });

const me = await client.me();                         // this host's key: { label, keyId, publicKey, id }
const bob = await client.registerKey(bobsPublicKey);  // an rdb_keys id, for key columns
db.prepare("INSERT INTO user_identities (key_id, name) VALUES (?, 'Bob')").run(bob);
db.prepare("INSERT INTO user_caps (label, grantee_key_id) VALUES ('writer', ?)").run(bob);

client.events.watch((events) => { /* failed writes: table, local id, reason */ });
const status = await client.status();
if (isHostStatus(status) && status.upgradeRequired) { /* ask the user to update the app */ }
```

- `me`**,** `registerKey` **and** `events` work from `host.json` and the projection, where `rdb_keys` and `rdb_op_events` live, so they work while the host is stopped too, and never need the keystore. Writes the app makes then wait in the outbox for the next start.
- `status` **and** `watchStatus` come from `run/rhost.sock`: the running process's view, peers and the last error included. Without a running process, `status` is a stopped status with what `host.json` says, and `watchStatus` waits for the host to start.
- **The socket is read-only.** Nothing that signs goes through it; `rhost deploy` unlocks the key in its own process.



### Embedding rhost

The recommended setup keeps all configuration in the app folder, even when rhost runs inside the app rather than in its own processes. The same folder then works with the CLI.

```ts
import { openApp } from '@hyper-hyper-space/hhs3_rhost_node';

const app = await openApp('./my-app');
await app.start();                     // every host

const gaming = await app.create('gaming', { key: 'me', mesh: { scope: 'internet' }, name: 'Gaming' });
// or app.join(databaseId, 'gaming', { key: 'me', mesh: { scope: 'internet' } })
await gaming.start();                  // create and join don't start it
gaming.onStatus((status) => { /* same fields as rhost status */ });
const client = gaming.client;          // the rhost_client interface, in process
// ...
await app.stop();
```

`create` and `join` take the host's key, by label or `#<key id>`, its passphrase source, and its network settings, and write them to `host.json`. In process, all the hosts share the app's process, and the host is still the unit of start and stop: `app.start(name)` and `app.stop(name)` act on one. `app.hosts()` lists the hosts, `app.host(name)` returns one, and `app.remove(name)` removes this device's copy. An embedded host takes the same lock file as `rhost serve` and listens on the same `run/rhost.sock`, so the CLI reaches it the same way and the two never serve it at once. The in-process client calls the host directly; its key and event calls go through the running projection, so they need the host started.

A browser has no folder and no socket. Pass the same `app.json` as an object, with the release files parsed from their bytes, and the browser platform (`rhost_browser`) keeps each host's record, replica and projection, and the keys, in IndexedDB. File mounts go in the origin private file system. The client in the same tab is the in-process one. Other tabs reach it with `rhost_client_browser`, over a BroadcastChannel, and a Web Lock takes the place of `run/rhost.lock`.

`serve(app, host)` is what a tab calls. The tab that gets the lock runs the host. A tab that finds the lock held stays queued, and `serve` resolves once the current host has answered status; when the holder closes, that tab starts the host. A tab that never calls `serve` stays a client. `stop()` tells the queued tabs not to start. The next `serve()` clears that.

```ts
import { Rhost } from '@hyper-hyper-space/hhs3_rhost';
import { browserPlatform, serve } from '@hyper-hyper-space/hhs3_rhost_browser';
import { parseReleaseFile } from '@hyper-hyper-space/hhs3_rpack';
import config from './app.json';

const text = await (await fetch('/catalogs/editor-2.0.1-5d0e4b19.rpack')).text();
const app = await Rhost.open(config, browserPlatform({
    name: 'editor',
    releases: [parseReleaseFile(text)],
    prompt: async (key) => askTheUser(key.label),
}));
if ((await app.hosts()).length === 0) await app.create('default', { key: 'me', mesh: { scope: 'internet' } });
await serve(app, 'default');
```
