## Summary

Our plans, critiques, and reference docs sit side by side across the repo, and nothing says which of them describe the code as it is. This HIP separates the two jobs. Module docs describe only current behavior. Every proposed change, whether to the design, to the implementation, or to how we work, is a numbered HIP in `hips/` that opens with a standard header and summary. It also maps the existing plans and critiques to HIPs 2 to 19 and lists the module-doc edits that follow.

## Why

In the last few weeks we started writing a document before most changes, critiquing it, and revising it. The result is about sixty files spread over `modules/rdb/plans/`, `modules/rpack/critique/`, `modules/rdb_react/plans/`, the repo root, and the modules themselves. Nothing says which of them describe the code as it is, which are proposals, which were implemented, and which were abandoned. Some concrete problems this causes today:

- **A proposal inside a reference doc.** `rpack/IMPLEMENTATION.md` ("Advancing an observed version") says that `ALLOW UPDATE REF` is read in the observed group's frame today and describes the observer frame as a follow-up. The observer frame landed on 2026-11-04, with a design that differs from that section on every point it makes, and the section still says the opposite.
- **Broken links.** `rhost/README.md` links `../rpack/DESIGN.md` and `../rpack/ARCHITECTURE.md`. Both files now live in `rpack/critique/`.
- **Plans with stale statuses.** `RCAP_INCREMENTAL_BOUND_WALK.md` calls RSet's adoption of the bound walk "next" and a prerequisite for Phase 5. Both landed (`d3537ca`, `662b96b`). `RDB_OBSERVE_FIX_PLAN_v2.md` describes a `computeSafeFloor` that never reached the code: the single-pass widening walk (`cfce04f`) replaced it. Neither file says so.

Python's PEPs and the IETF's RFCs solve this by splitting two jobs. A numbered proposal records *why* something was decided. The documentation says *what is true now*.

## The rule

**A module doc states, a HIP argues.**

- Module docs (`modules/<m>/README.md`, the reference docs and `SPECS.md` files they link) describe current behavior. They never describe planned behavior. They link the HIP instead ("observer-frame gates: see HIP-14").
- A HIP describes a change: why, what, what was considered. When it lands, the module docs take over the description, and the HIP is no longer updated.

## Format

One file per HIP, flat in `hips/`:

```
hips/
  README.md                          # index: number, title, type, status
  0001-hips.md
  0007-ideal-concurrency.md
  0015-certified-checkpoints.md
  0015-certified-checkpoints.review-1.md   # only while 15 is a draft
```

Every HIP opens the same way: a title line, a header, and a *Summary*. What comes after the summary depends on the HIP.

```markdown
# HIP-7: Ideal concurrency (`ANY`) for barrier checks

- **Type:** design
- **Status:** implemented
- **Modules:** rdb, mvt, std_types
- **Requires:** —
- **Superseded by:** —
- **Implemented in:** `d8bbd49`

## Summary

One paragraph, readable on its own: what changes, and why.

## Why

...
```

### Header

Every field is always present, with `—` when it does not apply, so the state of a HIP can be read, or grepped, at a glance.

- **Type** says what kind of change it is:
  - `design` changes what the system does: the semantics of a data type, an API, a wire format.
  - `implementation` changes how the system does it, with no observable difference: an optimization, a refactor, a new internal algorithm (HIP-10, HIP-12).
  - `informational` proposes nothing by itself: a survey, a list of ideas, prior art (HIP-18, HIP-19).
  - `process` changes how we work (this HIP).
- **Status** is one of `draft`, `implemented`, `deferred`, `withdrawn`, or `superseded`. Informational and process HIPs use `active` in place of `implemented`.
- **Modules**: the modules whose code or docs the HIP changes.
- **Requires**: HIPs that must land first.
- **Superseded by**: set together with status `superseded`.
- **Implemented in**: the commits that carry the work, set together with status `implemented`.

The header is the only part of a HIP that changes after it lands.

### Summary

The first section of every HIP: one paragraph, a few sentences, that tells a reader what the HIP changes and why, so they can decide whether to read the rest. An implementation HIP also says what it leaves unchanged.

The summary describes the proposal, not its progress. Words like "next", "done", or "in progress" belong in the header. A summary that never mentions progress cannot go stale when the work lands, which is how the plans listed under *Why* went stale.

### Body

The sections our recent plans already use, in this order, each only when it applies:

- *Why*: the problem, with evidence: a failing case, a measurement, the code where it happens.
- *Design*: what changes. For an implementation HIP, the new mechanism.
- *Why it is sound*: the argument that the design is correct. For an implementation HIP, why behavior is unchanged.
- *Changes*: the files and functions touched, in the order they land.
- *Tests*: what is added, and what each test pins down.
- *Considered and not taken*: alternatives, and review findings that were declined, each with the reason.
- *Open questions*: what is still undecided.
- *History*: for a migrated HIP, the files it came from (see below).

An informational or process HIP needs only the *Summary*. The rest of its body is free-form.

## Process

1. Take the next number and write `NNNN-slug.md` with status `draft`.
2. Revise it in place. Git keeps the earlier versions.
3. A critique can sit next to it as `NNNN-slug.review-N.md` while the HIP is a draft. When the HIP is settled, its outcome goes into *Considered and not taken*, and the review files are deleted.
4. When the work lands: set **Status** and **Implemented in**, update the module docs, and add the HIP to the **HIPs** line at the end of each affected README, for example `**HIPs:** [7](../../hips/0007-ideal-concurrency.md), …`.

## Migrating what we have

For each chain of files, the HIP is the last plan in the chain, with the header and a *Summary* added at the top and a short *History* section at the end. That section lists the files it came from and the commit where they can still be read (`git show <commit>:<path>`). A file the HIP's text depends on for an argument it does not contain is folded in as a section (the table says which). The other files are deleted.

Before deleting a critique, check that its findings either made it into the plan or are worth a line in *Considered and not taken*.
